# Telegram-бот учета продаж сотрудников магазина одежды

Бот принимает ежедневный текстовый отчет от администратора, автоматически разбирает его (сотрудники, касса, онлайн-продажи, бонусы), считает планы и выполнение, и предоставляет статистику, расчет зарплаты и экспорт в Excel.

## Стек

- Python 3.12
- aiogram 3
- SQLAlchemy 2.0 (async, SQLite по умолчанию, легко переключить на PostgreSQL)
- pandas + openpyxl (экспорт в Excel)
- python-dotenv

## Установка

Распакуйте проект и перейдите в его директорию:

```
cd tg_sales_bot
```

Создайте и активируйте виртуальное окружение:

```
python3.12 -m venv venv
source venv/bin/activate        # Linux / macOS
venv\Scripts\activate           # Windows
```

Установите зависимости:

```
pip install -r requirements.txt
```

Создайте файл `.env` на основе примера:

```
cp .env.example .env
```

Откройте `.env` и укажите:

- `BOT_TOKEN` — токен вашего бота, полученный у @BotFather
- `ADMIN_IDS` — Telegram user_id администраторов через запятую (узнать свой id можно у бота @userinfobot). Если оставить пустым — доступ к админ-командам и `/import` будет у всех пользователей.
- при необходимости — `DEFAULT_PLAN_CONSULTANT` / `DEFAULT_PLAN_ONLINE` (планы по умолчанию для новых сотрудников, создаваемых автоматически при импорте отчета).

## Запуск

```
python -m bot.main
```

При первом запуске бот автоматически создаст файл базы данных SQLite (`sales_bot.db`) и все необходимые таблицы.

## Переход на PostgreSQL

Замените в `.env`:

```
DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/sales_bot
```

и установите драйвер:

```
pip install asyncpg
```

Больше никаких изменений в коде не требуется — SQLAlchemy сам работает с любой указанной СУБД.

> **Важно про роль `intern`:** поле `role` в таблице `employees` хранится как нативный Postgres `ENUM`-тип. Если база уже создана и вы добавляете новое значение роли (например, `intern`) уже после первого запуска на PostgreSQL/Supabase, `CREATE TABLE`/автосоздание таблиц новое значение в существующий enum-тип не добавит. Нужно выполнить миграцию вручную, один раз, в SQL Editor:
>
> ```sql
> ALTER TYPE roleenum ADD VALUE 'intern';
> ```
>
> Если не уверены, как называется enum-тип в вашей БД, сначала проверьте:
>
> ```sql
> SELECT t.typname, e.enumlabel
> FROM pg_type t
> JOIN pg_enum e ON t.oid = e.enumtypid
> WHERE t.typname ILIKE '%role%';
> ```
>
> Выполняйте `ALTER TYPE ... ADD VALUE` отдельным запросом, не в одной транзакции с последующей вставкой сотрудника с этой ролью.

## Формат текстового отчета

Бот понимает как классический формат (значения через тире), так и вариант без тире / с сотрудниками смены каждым на отдельной строке. Пример:

```
Дата: 13.07

Количество чеков - 64

Безнал - 553.900
Наличными - 245.000

Общая Выручка
План / Факт - 798.900

Средний чек - 13.741

Конверсия - 51%

Онлайн продажи: 76.930

Вообщем: 875.830

Клиентов вообщем: 124

Товара продано: 96

Бонус:
Алина - 2000
Диас - 2000

Смена:
Арман, Алина, Жасулан

Касса:
Арман - 399.450
Алина - 399.450

Смена открыта: 11:00
```

Логика разбора:

- Из блока `Смена` извлекается список всех сотрудников смены.
- Из блока `Касса` извлекаются суммы консультантов.
- Сотрудники из смены, отсутствующие в блоке `Касса`, считаются онлайн-менеджерами.
- Сумма из строки `Онлайн продажи` делится поровну между всеми онлайн-менеджерами (функция `distribute_online_sales` в `bot/services/distribution.py` — вынесена отдельно, чтобы алгоритм распределения можно было легко изменить, например, сделать пропорциональным).
- Если сотрудника нет в базе — он создается автоматически с ролью `online` (если это онлайн-менеджер) или `consultant` (если он есть в кассе), и планом по умолчанию из `.env`. Роль `intern` автоматически при импорте не назначается — она выставляется вручную через `/set_role` (см. ниже).
- Повторный импорт отчета за уже существующую дату заменяет старые данные (счетчик смен корректно откатывается перед заменой).

## Роли сотрудников

| Роль | Описание |
|---|---|
| `consultant` | Обычный сотрудник в зале, продажи считаются по блоку "Касса" |
| `online` | Онлайн-менеджер, продажи — доля от "Онлайн продажи" |
| `intern` | Стажер (полставки): оклад за смену и % от продаж — **половина** от обычной ставки. Выполнение плана считается как обычно, без изменений |

## Формулы расчета

### Статистика и план

```
план = количество_смен × дневной_план_сотрудника
процент_выполнения = продажи / план × 100
средняя_касса = продажи / количество_смен
```

### Зарплата (`/salary`, `/salary_all`)

```
% от продаж (шкала по выполнению плана):
  ≤ 80%     → 1%
  81–90%    → 2%
  91–109%   → 3%
  ≥ 110%    → 4%

Оклад по смене × количество смен + продажи × (% от продаж / 100) = зарплата
```

Для сотрудников с ролью `intern` оклад за смену и `% от продаж` домножаются на **0.5** относительно обычной ставки. Выполнение плана (`процент_выполнения`) считается точно так же, как для остальных ролей, без изменений — множитель влияет только на итоговую сумму, а не на саму планку.

Премии/бонусы из отчетов (строка `Бонус`) в расчет зарплаты не входят — считаются отдельно, как разовая выплата.

## Логирование

Логи пишутся в stdout через стандартный модуль `logging` (уровень INFO). При необходимости настройте вывод в файл в `bot/main.py`.

> ⚠️ В `bot/main.py` подключен `DebugLoggingMiddleware`, который логирует полный текст каждого входящего сообщения (включая текст отчетов с выручкой и бонусами сотрудников) на уровне INFO. Он был добавлен временно для диагностики пропавших апдейтов. Рекомендуется отключить его или понизить до уровня DEBUG в проде, если логи доступны кому-то за пределами узкого круга администраторов.
